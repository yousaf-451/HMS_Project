# HMS — Hospital Management System
## Prototype Documentation

**Frontend:** HTML5, CSS3, vanilla JavaScript (no framework).
**Backend:** one small Python server (`server.py`, standard library only).
**Database:** SQLite file `HMS_DB/hms.db`, created from `HMS_DB/schema.sql` (16 tables; see the database report).
**Data:** fictional dummy data only. No real patient data.

> **Important:** this is a course prototype. It has a real database and server-side rules, but it is **not** production software
> (see section 9). Browser `localStorage` is no longer used for the hospital data.

---

## 1. How to run

1. Open the project folder in VS Code and press **Ctrl+Shift+B** (or run `python server.py` in a terminal; Windows `py server.py`).
2. The browser opens http://localhost:8000. Log in with `admin@hms.test` / `Admin@123`. The server checks the password against the `users` table.
3. Use **Reset demo data** (header, desktop) to empty the tables and reload the dummy data.
4. Open `http://localhost:8000/selftest.html` (after logging in) for the in-browser checks. `python tests/test_api.py` tests the server and database.

## 5. Data and validation approach

Validation has three layers:
1. **HTML5 attributes:** `required`, `type="email|tel|date|number|time"`, `min`, `max`, `maxlength`, `pattern`.
2. **JavaScript rules** (`validation.js` and each module): uniqueness, cross-field rules, date rules, stock rules.
3. **Feedback:** an inline error under the field (with a ⚠ icon), a red toast on a failed submit, a green toast on success, `aria-invalid` on bad fields, and the first bad field gets focus.

The forms use `novalidate`, so the JavaScript messages are shown instead of the browser's default bubbles.
Errors appear when you leave a field (blur) and again when you submit.

Shared formats: **phone** `03XX-XXXXXXX`; **dates** `YYYY-MM-DD`; **money** at most 2 decimals.
IDs: `PAT-0001`, `DOC-001`, `APT-0001`, `REC-0001`, `INV-0001`, `MED-0001` (generated automatically except Patient, Doctor and Medicine, which are editable but must be unique).

**Calculation (done in JavaScript, shown live):**
`Subtotal − Discount = Amount after discount`, then `+ Tax (after-discount × rate%) = Total`.
Example: items 50 + 30 + 25 = 105; discount 10 → 95; tax 5% = 4.75; **total 99.75**.

**Medicine form**

| Field | Type | Required | Format | Length / Range | Unique | Validation rule |
|---|---|---|---|---|---|---|
| Medicine ID | Text | Required | `MED-0000` | 8 | **Yes** | Format check; must not already exist |
| Medicine Name | Text | Required | Letters, digits, space, `- . / ( ) % +` | 2–60 | No | Pattern check |
| Category | Select | Required | From the list | n/a | No | Must be selected |

| Quantity | Number | Required | Whole number | 0–100,000 | No | Range, integer only |
| Unit | Select | Required | Tablets / Capsules / Bottles / Tubes / Vials / Sachets | n/a | No | Must be selected |
| Price per unit ($) | Number | Required | Max 2 decimals | 0.01–10,000 | No | Range; at most 2 decimals |
| Expiry Date | Date | Required | Valid date | After today, within 10 years | No | New medicine cannot be expired; an old expired date may stay unchanged when editing |
| Batch Number | Text | Required | Letters, digits, `-` (saved in uppercase) | 3–20 | **Yes** | Pattern; not used by another medicine |

**Stock update form:** Action (add / remove / set exact), required. Amount, required, whole number: 1–100,000 for add and remove, 0–100,000 for set exact. The result must stay between 0 and 100,000, and you cannot remove more than the current stock.

**Dispensing form:** Patient, required. Medicine, required (expired and out-of-stock medicines are not offered). Quantity, required, whole number from 1 up to the available stock. Amount = unit price × quantity.

**Computed stock status** (never typed): *Expired* if the expiry date has passed; else *Out of Stock* if quantity is 0; else *Low Stock* if quantity is 20 or fewer; else *In Stock*. Medicines expiring within 30 days get an extra warning.

## 8. Accessibility and responsive design
- Semantic HTML, a label on every input, "Skip to main content" link.
- Visible keyboard focus, modals trap focus and close with Esc.
- Status is never shown by color alone: badges, alerts, timeline and notifications all use an icon and text.
- `prefers-reduced-motion` is respected.
- Media queries at 900px, 700px and 600px; tables scroll inside their cards; the sidebar becomes a slide-in menu on tablets and phones.

## 9. Limitations (prototype only)
- **Frontend data layer:** the pages send the whole list (e.g. all patients) to the server on each save and the server works out what changed. This keeps the page code simple but would not scale; a production API would use one request per record (`POST /patients`, `PUT /patients/12` …) and asynchronous calls.
- **Login:** one demo user, an in-memory session cookie (lost when the server restarts), no password reset, no lock-out after wrong attempts, and no HTTPS. **Roles exist in the `users` table but are not enforced yet.**
- **Server rules:** the date and stock rules (R1 to R8 in the database report) are enforced in `server.py`; the structural rules (keys, formats, ranges) are enforced by the database itself. The browser repeats them for friendly messages.
- **SQLite** is used because it needs no installation. The schema is written in PostgreSQL style for a later move to a server database.
- All data is dummy data. No real payment processing; "Mark as paid" only changes a status.
- No real pharmacy or hospital integration.
- Dashboard "Recent Activities" and "Available Beds" are fixed sample content (beds are not in the database design).
- Medical records and invoices have no Delete button (invoices can be cancelled). Patients, doctors and medicines can only be deleted when nothing else refers to them: the **database refuses** otherwise (ON DELETE RESTRICT).
- Search is simple text matching done in the browser.
